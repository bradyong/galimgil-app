## 2. 기존 엔진에서 의미 오염이 발생했던 원인

### 코드에서 확인한 경로

1. `app.js`의 `findFeatureEntry`는 선택지 문자열에 키가 포함되는지 `includes`로 검사한다. 단어 경계나 문맥 의미를 이해하는 방식이 아니다. 일치한 키 길이에 분류 일치 보너스 1000을 더하므로, 먼저 잘못 분류되면 짧고 무관한 키의 특징이 우선될 수 있다.
2. `inferredOptionProfile`의 분류별 공통 설명, subject profile, 추출된 특징이 이후 판단과 출력에서 섞였다. 그럴듯한 특징 목록이 존재한다는 사실과 질문에서 실제 비교 근거를 확보했다는 사실이 분리되지 않았다.
3. 초기 AI 의미 해석 경로는 질문을 해석해도 기존 `decisionEvidence`를 교체하지 않았다. 따라서 의미 구조는 정상인데 실제 승자 계산에는 잘못 분류된 특징이 남는 이중 경로가 있었다.
4. 기존 category, forced 선택, strong-context 보정 등의 영향까지 보존하면서, '승자/점수가 바뀌지 않는다'를 긍정적 결과로 취급했다. 잘못된 판단을 보존할 위험을 놓쳤다.
5. 출력에서도 실제 차이보다 category fallback이나 행동형/daily 고정 문장이 우선하면 서로 다른 질문이 비슷한 설명으로 수렴했다. 문장만 바꿔서는 상류의 잘못된 근거가 해결되지 않는다.

## 3. semantic-v2가 해결한 부분과 재사용할 아이디어

- 상황, A/B 의미, 실제 차이, 판단축, 근거 출처, 불확실성을 공통 구조로 관리했다.
- 기존 규칙으로 충분한 질문에는 AI를 호출하지 않는 경계를 유지했다.
- 검증된 AI 의미 구조를 채택한 저신뢰도 질문에서는 기존 category fallback과 무관한 특징을 제외하고, 정규화한 판단축으로 `decisionEvidence`를 구성했다.
- AI가 승자를 정하지 않고 기존 코드가 점수를 계산하도록 역할을 분리했다. base/card/zodiac 기여와 태그 일치를 추적할 수 있게 했다.
- 비용·시간·성능 등의 우열을 모르면 임의 가중치를 만들지 않았다. 우열 근거가 없는 결과는 놀이용 선택이지 객관적 최선이라고 설명하지 않는다.
- 모델이 uncertainty를 낮게 적어도 의미의 단순 반복, 공허한 차이, 잘못된 축, 근거 없는 주장 등을 별도로 검사했다. 버린 축도 기록했다.
- 녹차/홍차의 부정확한 새 비교축과 의미 없는 조어는 확인 대상으로 남겼다. 통과율을 높이려고 거짓 근거를 채우지 않았다.

출력은 26건이며 나머지 2건은 의미 확인 대상이다. 예측형 검사는 '것이다/하게 된다/예상된다/가능성이/할 수 있다'를 포함한다. 명사구 검사는 종결형 기반의 휴리스틱이다. 중복 수는 내용어·인용구 치환 후 고유 틀을 제외한 초과 수다. 이 지표들은 재미·공유성의 합격 판정을 대신하지 않는다.

### 확인된 실패 경로

1. **재료가 충분하지 않았다.** 저장된 scene에는 단순 명사구나 설명형 예측문이 많았다. 로컬에서 어미를 바꾸는 것만으로 구체적인 반전·자기합리화·공감을 만들 수는 없었다.
2. **프롬프트 지시가 출력 품질로 이어지지 않았다.** 별도 Writer 초안도 캡처를 라벨로 쓰거나 딱딱한 설명체를 유지했다. 일부 anchors는 검증된 의미가 아니라 이전 출력 초안을 인용했다.
3. **표현 개선 과정에서 사실이 추가됐다.** 비용상 이점, 더 빠른 흐름, 집중력 향상, 상대 반응 등의 근거 없는 혜택이 이유 초안에 들어갔다. 해당 AI 이유를 그대로 사용자에게 출력하지 않았다.
4. **안전한 로컬 이유가 반복을 악화시켰다.** 검증된 활동과 점수 근거만 설명하도록 제한했지만, 좁은 공통 문장 틀에 수렴하여 이유 중복이 7/26에서 22/26으로 증가했다.
5. **탈락 시 기존 초안으로 돌아가 문제가 남았다.** 유효 의미 18건 중 Writer 13건이 탈락했고 기존 scene 초안으로 돌아갔다. 의미 처리와 앱 흐름은 유지했지만 문장 품질 목표는 충족하지 못했다.
6. **형식 통과와 재미는 달랐다.** 통과한 5건도 재미나 근거 적합성이 보장되지 않는다. 완전히 같은 문장이 없다는 사실도 문장 틀·어투·역할 중복이 해결됐다는 뜻이 아니다.

### 실험 범위의 정확한 구분

- 실제 유료 실험 20회는 **저장된 semantic-v2 의미를 고정한 Writer 평가**였다.
- 신규 질문에 의미와 Writer를 한 응답으로 받는 코드 경로는 모의 응답 테스트로 확인했다. 신규 의미 생성까지 포함한 통합 품질·지연·비용을 실제로 검증한 것은 아니다.
- 재호출 없이 입력 24,397 / 출력 4,246토큰을 사용했다. 당시 공식 단가 환산 $0.01459125로 승인 상한 $0.05 이내였다. 청구서 실결제액은 확인하지 않았다.

## 6. 폐기해야 할 접근

여기서 폐기는 파일 삭제가 아니라 **다음 구현의 기본 접근으로 다시 채택하지 않는다는 뜻**이다.

- 잘못된 승자·점수까지 보존하면서 불변을 성공 기준으로 삼기.
- 키워드 일치나 공통 fallback 특징을 실제 질문의 이해 근거로 취급하기.
- AI 의미 구조는 설명에만 붙이고, 점수에는 무관한 기존 특징을 남기기.
- uncertainty=low, 형식 통과, 문장 완전 일치 없음만으로 이해·재미가 해결됐다고 보기.
- 내부 축 이름·영문 enum을 사용자 설명으로 그대로 출력하기.
- `scene.future`의 예측형 문장이나 선택지 라벨을 최종 재미 콘텐츠로 취급하기.
- 새 고정 문장, 단어 사전, 샘플별 예외·드립을 계속 추가하기.
- 안전성 문제를 모두 같은 범용 이유 문장으로 덮기.
- 재미를 위해 가격·성능·타인의 반응 등 근거 없는 사실을 추가하기.
- 평가 표본을 바꾸거나, 검증 기준을 낮추거나, 반복 API 재시도로 실패를 가리기.
- Writer 전용 평가를 신규 의미+Writer 통합 실서비스 검증으로 보고하기.
